# Independent map animations

The native camera can stay parked while the renderer shows another part of the map. Visible units, city disorder/fireworks and tile effects in those renderer views must continue animating. Reading a unit record beyond the native camera is insufficient: the native animation tick previously advanced only the viewport's unit and effect arrays.

`civ3-bridge::unit_views` hooks the existing PCGames `Units_Image_Data` update at `0x405FF0`. It supplies temporary unit/effect arrays to that one original invocation. The elapsed float stack word passes through unchanged. The native function still advances the selection cursor, each selected unit, its displayed army member and every loaded effect. Shared entries are deduplicated, so an object shown by several views receives one update. UI animation preview callers retain their own arguments.

The full-map unit selector runs on the game thread at most once every 33 ms and caches only unit IDs. The current unit's tile and the explicitly pending animation tiles are refreshed each native call, so a newly selected or moving stack does not wait for that cache. Each tick resolves those IDs again and checks the native suppression, visibility, detector and fog rules before use. Loaded units do not acquire separate animation ticks. The unit snapshots are copied after the native update, so the publisher receives the current frame. A failed post-update snapshot cannot escape into the generic hook fallback and cause the native update to run twice.

City and tile effect pointers are read fresh on the game thread. Only effects on currently visible tiles join the update array. Their visibility test uses the same four tile words and `Leader.ID` as the native effect collector. Previously explored fog is insufficient. Global extra animations, including aircraft bombs and SAM/SDI shots, remain in the original vector and are kept once. The native collector still owns tile-effect expiry and deletion. No effect pointer or unit pointer survives the invocation. `Civ3::effects()` already reads all city/tile effects for rendering, so these updated frames reach every renderer view.

Visible independent units also receive the native animation-membership byte at `Unit+0x24D`. Otherwise `0x4EEC97` cancels pending animations and `0x406963` seeks worker animations instead of queuing them. The bridge tracks only its additional member IDs, clears stale membership and mirrors the builder's loaded-animation reset at `Unit+0x3A8` before the next list build. A unit entering the native list retains that list's own membership. The separate selectable-unit byte at `Unit+0x24C` is untouched.

The temporary arrays do not overwrite `Animator.Units`, its effect vector, their capacities or the City screen's internal viewport. The native list-build hook first reapplies the parked main-camera bounds through `native_camera::maintain` and then calls the original builder. Camera parking is installed only after both animation hooks succeed.

The PCGames ABI was checked against both the unmodded and C3X-modded executables. At `0x4EF228` the caller pushes the effect-vector address, unit count, unit-array address and elapsed float word, then calls `0x405FF0` with `ECX = 0x73DA00`. The callee reads those four arguments and returns with `ret 0x10` at `0x406142`. Its effect loop reads vector begin/end at offsets 4 and 8. Unit creation and restore load their FLC data at `0x569971` and `0x5903F3`, independently of viewport collection. GOG and Steam hooks remain unavailable until their binaries are decoded.

The Fortify order (`0x4D8930`, reached only from `issue_command`) tests its tile with `Main_Screen_Form::tile_in_view` (`0x4E6AB0`) at `0x4D8949`. That test reads the parked bounds. In view, the order plays the blocking FORTIFY one-shot (`0x4F01B0`), which runs animator ticks until the last frame. The FLC type change in that tick (`0x4026A0`) starts the action's sound through `0x405960`. Out of view, it only requests FORTIFY, and `Unit::set_state` (`0x5B2D50`) immediately replaces the request, so neither the animation nor the sound plays. A call-site hook at `0x4D8949` keeps the native answer. While parking is active it also answers "in view" for an on-map tile that the player currently sees, using the effect visibility words above. Fogged tiles keep the instant fortify. Movement (`0x5BCF30`) and combat (`0x4A1D60`) never use this test.

The worker orders Railroad, Mine, Clear Forest, Clear Jungle and Build Barricade (`0x4DB2CC`, `0x4DB403`, `0x4DB49F`, `0x4DB52A`, `0x4D90C8`) gate their looping job-animation request on the same test before setting the job state. They remain unchanged here.

Focused tests cover object deduplication, elapsed-word preservation, post-update capture ordering, the snapshot-panic fallback, immediate active-stack replacement before cache expiry, cached-unit visibility changes, loaded/dead units, each current-visibility effect word, stale membership removal and native-member preservation. A 32-bit memory test checks that membership writes preserve every unrelated byte, including the selectable-unit flag. Runtime checks should include an idle unit, a moving or fighting unit, an army, city disorder/fireworks and a tile effect far from the parked native camera. They should also check fog and invisible units, with both A and B looking away from the native origin.

## Unit slides

With "animate movement" on, `0x5BAB70` slides a moving unit to the next tile through `Unit::slide` (`0x5BA8C0`, `__thiscall`, `ret 0x10`): `(to_x, to_y, steps, ms)`, called with 9 steps and 100 ms (50 ms in its other case at `0x5BAE54`). The slide divides `ms` by 10 while Shift is down and Caps Lock off, or Caps Lock on and Shift up (`0x5BA913..0x5BA949`). After each of its `steps - 1` intermediate positions it calls `Animator::draw` (`0x4EED00`, at `0x5BAAED`), but only while that step is not late: the ms since the start must be below `k * ms / steps`. It never waits. A slide therefore lasts as long as its frames take. Natively eight frames of about 1.5 ms take 12 ms, so the unit jumps. Emulated on Apple silicon, a frame takes tens of milliseconds, most steps are skipped, and a tile shows the unit in one or two places. That was the "two frames a second" movement. With the option off there is no slide at all.

While the camera is parked, `civ3-bridge::unit_slides` hooks the slide's start and its frame call. At the start it records the unit, its tile, the one-tile way (`64*dx, 32*dy` full-size pixels, also across the wrap) and the length after the Shift rule, and wakes the publisher. The first frame call draws as before: the animator's list then holds the unit under the moving one, and the tick starts the walk and refreshes the units read beyond the camera. Every later step sleeps until its threshold instead of drawing. The slide then lasts its `ms` in the game too, unless that one frame takes longer. The sleep counts as game time in `inproc::hook_time`.

The publisher draws a sliding unit's pieces as free sprites at the start of its way, after the units pass, and tells the slide once as a `scene::Motion` over exactly those sprites: a serial, the way and the length. The viewer starts the motion's clock when that batch arrived (`scene::Display::motion_arrival`) and moves the sprites along the whole way at its own frame rate; a resent serial keeps its clock. The picture trails the game by the publisher's latency (a round, tens of ms emulated) rather than skip the start of the way. The motion is told until 250 ms after the slide's end, and the viewer holds the sprites at its end. Afterwards a unit still on its old tile (the slide puts its picture back there before `Unit::move`) is drawn at the end of the way for up to 500 ms. The other units on the slide's first tile stay as the slide's first publication had them while it is told, because the game stops listing the unit under the moving one when the slide ends, and the units beyond the camera are only read again at the next animator frame. The publisher does not skip a round as unchanged while a slide is told.

`civ3-bridge::anim_steps` logs windows of the animator's frames that had a unit moving or a frame of 100 ms or more: frames, mean and longest interval, the game thread's CPU time per frame, its time in our hooks, its memory reads and writes per frame (`inproc::mem::thread_accesses`), and the hooks that took most. Viewer frames of a slide are traced with `TILE_VIEWER_MOTION_TRACE=1`.

## On the viewer's clock

The selection cursor pulses on the renderer's own clock. The game's cursor (`Animator.Unit_Cursor_Animation`, docs/civ3-map-rendering.md §10.6) runs free on real elapsed time: 30 frames of `Cursor.flc`, each 2500 / 30 = 83 ms (header +0x6C over +0x62), with no restart on a new selection. The layers `unit_cursor` and `unit_over_cursor` therefore have `viewer_ms_per_frame = 83` (`tile_render_shared::HOST_CLOCK`): the GPU picks the frame from `FrameParams::host_tick_ms`. The cursor's translucent glow and the free-sprite path (slides, a scaled HUD, the smoke that takes a selected unit off the layers) use the same whole animations on that clock. The live reader passes the cursor's frame as 0, so the game's frame neither makes it jump nor starts a publisher round. A trace keeps its frame, which becomes the phase, so a picture of a trace shows the frame the game showed. The game still decides which unit has the cursor and hides it (`Animator+0x1914` bit 0) while a unit moves or fights and while the city screen opens. The cursor keeps pulsing while the game's thread sits in a modal loop. The renderer keeps a picture between frames only while no viewer-clock layer draws a cell (`TileWorld::host_clock_layers`).

The accessibility arrow's bob was already the viewer's (`tile_viewer::arrow_bob_offset`). These still follow the game's frames: unit animations (idle, fidget, actions, fortify, death, worker jobs: a per-unit state machine with sounds and one-shots that block the game thread), city disorder/fireworks and tile effects (the game owns their expiry), and leader heads. `unit_views` keeps these advancing for every visible unit, but they pause while the game's animator does.
