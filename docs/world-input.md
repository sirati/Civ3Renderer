# Map input outside the game's camera

An independent renderer camera can show tiles that the original game window does not show. Pointer motion over those tiles emits `scene::Input::WorldMove`; clicks emit `WorldButton`. Once the game advertises its semantic camera-focus stream, every actual map point uses this route, including points inside the old client rectangle. UI controls retain client-coordinate input. The bridge no longer clicks the minimap to make a world click reachable. Actual map pans still have their own `Look` messages.

For the decoded PCGames executable, a registered private window message delivers each virtual event on the game's thread, in the same OS queue as ordinary keys and UI input. A hook on `Main_Screen_Form::get_tile_coords_under_mouse` supplies the renderer's tile. Native hover and Base_Form button handlers then perform selection, city opening, context menus, go-to targeting and legal-action checks. The game remains responsible for visibility, movement and command validity. Ordinary mouse input clears the virtual tile.

The conversion uses the game's current normal or Z coordinate scale, including wrapped maps. The stored preview identity is a tile, independent of artwork scale. It never treats a normal-resolution zoom-box camera as a different input coordinate system. Native selection does not need to recenter the game camera. A scoped guard suppresses the native empty-tile recenter during virtual selection, while a newly opened city screen retains its native city focus.

A presented camera movement also refreshes the world point beneath a stationary pointer. This keeps G targeting and a held right-drag route current during edge scrolling, flings and focus changes. Released destinations stay fixed. Failed frame acquisitions and retained pictures awaiting compatible art do not retarget from an unpresented layout.

Consecutive pending moves replace one another without adding more OS messages. Preview updates coalesce in the same way. Keys, buttons, sliders and other UI events end that sequence. Camera-report metadata does not end it. Path finding runs on the game thread at most once per 33 ms for a moving target, while the renderer can continue drawing faster.

The Drag map mode (the Civ6 movement style) uses a separate go-to preview transaction. Right dragging changes the destination and right release keeps that preview. Holding the right button still for 0.35 s (`tile_viewer` `LONG_PRESS_SECONDS`) preselects the tile under it the same way. Only a quick right click, released sooner and not dragged, reaches the game as its right click (the unit or city menu, the tile box). The release of a long or dragged press is swallowed wherever it ends, on a city or a unit too. A later left click confirms only the same tile, selected unit and loaded world. A changed unit, map, command or destination consumes the confirmation without issuing a move. Cancellation always retires the transaction; Escape reaches only its own still-active command in a safe map state, never a dialog opened in the meantime.

### What keeps and what ends a preselected destination

The preselection used to end as soon as the pointer left the world: the viewer cancelled it for any pointer motion over the interface, any press off the world, any key and the wheel, so the game's own command buttons could not be reached with it. Now these keep it: moving over the map or the interface (the moves over the interface reach the game, for its buttons' hover), the wheel and map scrolling, dragging the map from the world (left or middle button), the pointer leaving the window or the window losing focus, Alt snapping, and keys and clicks on the interface. Those keys and clicks go to the game, which decides. These end it: a left click on the world (the confirmation, or on another tile no order at all), a new right press there, Escape, a screen or popup opening, the world closing, a change of the map movement mode, and any game command that no longer waits for a tile (Fortify, Sentry, Disband, another unit selected, the unit's turn over). The viewer follows the last case from `Interface::targeting`: once it has shown the command waiting, its end ends the preselection.

The game's orders that take the same tile keep it and change what it does (`civ3_bridge::world_input`, `Hold`). From their button or their key the game sets its own mode, and the bridge gives that mode the preselected tile, as the pointer resting there would (the main screen's timer and every map event check it). The confirmation is unchanged: the bridge hovers the tile and clicks the map through the game's own handler. The map's left click (0x4EB290) clears the mode and passes it with the tile to `perform_action_on_tile` (0x4E6E70), as a click of the player's would:

| Order | Game command | Mode (`Unit_Mode_Actions`) | Shown at the destination |
|---|---|---|---|
| go-to (the drag itself) | 0x10 | 1 | the red path, marker and turns (§10.15) |
| Move Units In Stack (X), of Same Type (Ctrl-X) | stack go-to 0x4ED390 | 0x12 | the same, the turns with a `+`, the stack button lit |
| Road to (Ctrl-R) | 0x40000008 | 2 | the tile frame and the order's pointer (`Art/Cursor.pcx` cell 2) |
| Rail to (Ctrl-Shift-R) | 0x40000010 | 3 | the tile frame and cell 3 |
| Colony to (Ctrl-B) | 0x40000004 | 0xE | the tile frame and cell 0xE |

0x4E2CF0 sets modes 2, 3 and 0xE without clearing the go-to's flag, so the bridge takes those modes whether or not it is still set (`targeting::carries`). The stack go-to starts at the unit's own tile (0x4DABC4), so the bridge gives it the tile again. The game draws the path only for the go-to modes and the tile frame for the others (0x4EF187). The renderer draws the same from the game's state, plus the order's pointer cell centred on the destination, because the real pointer may be anywhere by then.

While a destination is preselected, the bridge keeps the game's pointer tile on it (`live::pin`). A client mouse move over the interface keeps the virtual tile on the destination. A client press is made off the map, so a press that reaches the map itself, beside the interface's controls, can never give an order for some other tile. A key's world point does not move it either.

The native camera may park only while the private-message interceptor is attached to the live game window. Direct map events require the instrumented human-turn pump and no active animation or modal dialog. The existing advisor/Civilopedia input path remains responsible for its allowed actions while those forms are open. Builds without decoded native input sites retain their existing fallback.

## Popups opened at a map click

The game places a context menu (the right-click menu, the unit stack's list) with `Context_Menu_open` (PCGames 0x61A3B0): a top-level menu's top-left corner goes one pixel right of and below the mouse point, or its top-right corner there when bit 2 of its field 0x574 is set. Only when that leaves the screen does the game flip the menu to the other side of the point. The right-click tile information box (`open_tile_info`, 0x5AA530, form class 0x66F5C8) puts its top-left corner half a tile left of the tile's screen position and 9 pixels less half a tile height below it.

With the camera parked, the game gets a safe point in its tiny map instead of the click, so its own placement says nothing about where the click was. The bridge records the world pixel and tile of each virtual button before the native handler runs. When one of these two popups opens within two seconds, it publishes `Interface::popup_anchor`: the world pixel and the offset of the popup's corner from it, by the game's rule. The viewer then places the popup at that world pixel in the view the click was made in, the world cursor's view while the mouse is captured, scaled with the menus. The popup may cross the divider. If it would leave the window, the clicked view moves by the least whole world pixels that make it fit, as a pan by hand would. A view following the captured cursor moves only while the popup is open. Opening a popup never changes the point of interest while the camera is parked. Every other popup and screen follows the single screen place setting.

The tile box is drawn at the world's zoom in that view (`PopupAnchor::world_scaled`), never smaller than the HUD, because the game draws its picture of the tile as large as its map's tiles. Context menus keep the menu scale. A popup opened from an entry of an anchored one, such as a city menu's "Terrain details", belongs to the same click however long the menu was open. `open_tile_info` takes its tile from the map's pointer conversion. While such a popup is the modal form, the bridge keeps the virtual tile it was opened for: client mouse messages over the menu and world moves do not reset it. So the game shows the city's tile, and the anchor uses that tile.

While one of these popups is open, the map stays put: no edge scrolling, dragging, map wheel or captured motion. A press anywhere outside its body, or capturing the mouse again, sends `Input::DismissPopup` and does nothing else. On the game's thread the bridge synchronously delivers Escape, key and character (`WM_KEYDOWN`, `WM_CHAR` 0x1B, `WM_KEYUP`), on the window UI thread only if the popup is still open. This avoids queued duplicate dismissals reaching the map after the popup closes: the context menu's handler 0x61AA80 clears its selection and closes, and the tile box's 0x5AAFD0 closes on Escape or Enter. Both are a form's vtable +0x8C, which the game calls for Escape only from the character (see the routing notes in `modal-input.md`). The key alone, without its `WM_CHAR`, closed neither: the viewer sent its dismissals and the bridge logged them, but the menu stayed open. In the game a click beside the context menu does the same as Escape: its button handler 0x61A7D0 tests the point against the menu (`PtInRect`), closes it and clears its selection, and passes the click on only to a parent menu, never to the map. A world press that still reaches the bridge under such a popup dismisses it the same way and swallows its release. It shows no "Not while this window is open" notice; those are for full screens.

## Popups the viewer keeps

In the game both of these popups are modal. `Context_Menu_open` runs `Base_Form::m68_Show_Dialog` (0x6052F0) at 0x61A6F0 and returns the chosen row (`[menu+0x2190]`) to its caller. The map's right-click menu (`open_right_click_unit_menu`, 0x4E8910) then acts on that row from 0x4E99FC. `open_tile_info` runs the same loop at 0x5AAF6D and ignores its result. The loop pumps the game's messages until the popup closes, and `[0xCAD384]` sends all input to the popup meanwhile. With two views of one game, a popup in A would stop B too. The bridge used to drop B's map input while `dialog.depth != 0`, and a press in B only dismissed A's popup.

The tile box no longer works that way (`crate::detached`, `tile_viewer::layout::detached_popups`). A map click from the viewer runs its native handler inside `detached::scoped`. When that handler opens the tile box, the game draws and presents it as usual. At the first pass of its modal loop (the pump call at 0x6053B4, `modal::on_modal`), the bridge copies the box as the game presented it, frame included, from the committed UI frame. It then closes the box with Escape through the box's own key handler (0x5AAFD0). The loop ends and the game is back in its turn loop. To the game this is the same as a player who opened the box and pressed Escape, so no game state changes. If the box was not presented within 3 passes, the bridge keeps its canvas alone. If Escape does not close it, the box stays modal as before. While the scope runs, the publisher leaves the box's canvas out of the popups, so the viewer never treats it as a modal popup.

The bridge sends each kept box as an interface-only view (ids from 0x1000) and an entry in `Interface::detached`: its serial, anchor and the world pixel of the click. It keeps at most 4 and drops them all when a screen opens over the map. The viewer gives each new box to the view of its newest world press at that pixel and places it as it places a popup anchored at a click (`anchored_place`). A view keeps one box, and a newer one replaces it. Nothing in a kept box takes input. A press in its view, or on the box, closes it (`Input::CloseDetached`) and does nothing else, like a click beside the game's box. Esc with the pointer in that view closes it too and does not reach the game, where Esc would open the quit dialog. The other view plays on meanwhile, and both views can keep a box at once. A box chained from a menu entry ("Terrain details") runs inside the same scope and is kept the same way, at the menu's click.

`CIV3R_DETACHED_POPUPS=off` leaves the box modal, with the behaviour of the previous section. Context menus are still modal.

## Popups opened at a click on a screen

A screen can open a context menu too. A right click on a unit in the city screen's garrison strip (`Units_Rect`, City_Form+0x684C, the strip 295..768 x 715..768 of the 1024x768 screen) reaches `City_Form`'s right-click handler 0x420030 on the release. It finds the unit (0x420B60) and builds its menu with `Context_Menu_open` (0x4224C0 -> 0x61A3B0) at the click, whether or not the unit can still move. A unit that cannot move gets a one-row menu, "Activate". Base_Form calls that handler only when the press and release reach the same form (0x608AF0 records the form, 0x608B70 checks it).

These menus are not world anchored, because the click was not on the map. The bridge sets `Interface::popup_on_screen` instead when the open popup is a context menu or the tile box and a named screen is open. The viewer then keeps the popup where the game put it on that screen. It moves and scales with the screen, floating or placed in A or B, and it takes its clicks there. Without the flag, such a popup was treated as a modal over the screen (`scaling::MODAL_TOP`) and drawn near the top middle of the window, far from the click. On the city screen it covered the city's name and was easily missed.

## Validation

Automated coverage includes input wire round trips, normal/Z and wrapped tile conversion, hover beyond the original camera in free and captured modes, pending-move coalescing and input ordering, confirmation identity checks, and cancellation after a modal or unit change. The sys layer checks every native entry point against its recovered PCGames bytes before installing hooks.

For a controlled Wine or Windows game session:

1. Split the map into A and B. Pan B to a visible friendly unit outside the original game camera. Hover and select that unit without moving A. Right-click it and double-click a city to check the native context menu and city screen.
2. Press G and move the pointer across the original camera boundary into a distant renderer-visible tile. Check the destination cursor, red path and turn count continue to update. Confirm a legal destination once. Repeat with the pointer captured and with Z enabled, including the normal-resolution zoom box.
3. Check a wrapped map seam, an unreachable destination, a hidden enemy unit and an off-map black region. Native visibility and movement restrictions must still apply; leaving the map must clear the old destination overlay.
4. In Drag mode, right-drag a destination and release. Move the pointer elsewhere, over the HUD and the unit's buttons too; the preview must stay. Click the original destination to issue one order. Repeat but click another tile, select another unit, open a dialog, give an unrelated command (Fortify), lose focus or load another save before confirming. None of those cases may issue the stale order or close the new dialog. Hold the right button still on a city for half a second and release: no menu opens, and the tile waits for its confirmation. A quick right click there still opens the menu.
5. With a worker, preselect a destination, then click Road to (or press Ctrl-R): the destination shows the tile frame and the road pointer, and clicking it orders the road there. The same for Rail to, Colony to with a settler, and Move All (X or Ctrl-X, or the stack buttons) with a stack; the latter's turns show a `+`.
6. Open the Preferences and advisor panels, use relocated UI controls, then return to B. Ordinary UI input must restore client-coordinate lookup, and B's next world hover must restore its own tile.

Live native checks must use rebuilt matching bridge and renderer binaries because the input protocol changed. A test result from an older renderer does not validate these hooks.
